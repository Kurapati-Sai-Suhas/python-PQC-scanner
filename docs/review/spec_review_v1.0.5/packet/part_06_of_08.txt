PART 6 OF 8 — specification review packet (protocol v1.0.5)

5. **Hybrid flag.** `hybrid_component = yes` marks a quantum-vulnerable component that is combined with an approved PQC algorithm in a PQ/T hybrid construction (SP 800-227 Sec. 4.6, e.g. paramiko `mlkem768x25519-sha256`). The role is still recorded (e.g. `KEY_ESTABLISHMENT`); the policy treats the site as "no migration required, review the combiner".
6. **Scope attribution** (`app` / `test` / `vendored` / `example`) is recorded separately and never changes the role.
7. **One call expression per site.** A `try: load_a() except: load_b()` fallback pair, or two loaders feeding the same variable, are two sites with the same consumers and labels; provenance is never a composite value. When one candidate statement contains several supported calls, annotation guide v1.2 Step A fixes which call is the site.
8. **Ineligible negatives** carry `gt_role = NONE`, `assessability = DETERMINATE`, `key_provenance = n/a`, `obvious_from_name = n/a`, `evidence_needed = none`; they are scored at detection level only.
9. **`possible_roles` vs `secondary_roles`.** `secondary_roles` lists same-family alternatives of a determinate role (e.g. `VERIFY` next to `SIGN`). `possible_roles` is required for `UNKNOWN` and lists the cross-family candidates. The two are never mixed.

## 3. Assessability

| Value | Meaning |
|---|---|
| `DETERMINATE` | A careful human reader can fix one primary role from the repository at the frozen commit using the evidence scopes below. |
| `INDETERMINATE` | The role depends on a runtime value, dynamic dispatch, reflection or code outside the repository. The justified scanner action is to **abstain** (or to emit a dual/undecided target with an explicit reason). |

Assessability is a property of the site, independent of any tool's ability to resolve it.

## 4. Evidence scopes (what a reader needed to fix the role)

`call` (the call expression alone) → `function` (def-use inside the enclosing function) → `cross-function` (same module or class: attribute assignments, helper calls, one call level) → `cross-module` (another module in the repository) → `runtime-value` (cannot be fixed statically). The pilot records this per site in `evidence_scope`.

`obvious_from_name` is `yes` only when the role follows from the method name, given that the receiver is a public-key object of a supported library (its *type*, not its *origin*), or from a single-purpose algorithm name (X25519/X448 are key-agreement-only; Ed25519/Ed448 are signature-only), without inspecting the receiver's origin or consumers. The receiver-type condition matters because `encrypt`/`decrypt`/`sign`/`verify` also exist on AEAD cipher, HMAC and JOSE wrapper objects; "obvious" therefore means "obvious once the receiver is known to be an RSA/EC key", which is the T1→T2 step for an analyzer.

## 5. Key-provenance taxonomy (frozen)

| Provenance | Definition | Examples |
|---|---|---|
| `generated` | Key created in process by a key-generation API. | `rsa.generate_private_key`, `ec.generate_private_key`, `X25519PrivateKey.generate`, `RSA.generate`, `ECC.generate` |
| `loaded-PEM` | Parsed from PEM text. | `load_pem_private_key`, `load_pem_public_key`, `RSA.import_key(pem)` |
| `loaded-DER` | Parsed from DER bytes. | `load_der_private_key`, `load_der_public_key` |
| `loaded-SSH` | Parsed from OpenSSH formats. | `load_ssh_private_key`, `load_ssh_public_key` |
| `loaded-JWK` | Reconstructed from JWK/JWT parameters (`n`,`e`,`d`,`x`,`y`,`crv`). | `RSAPrivateNumbers(...).private_key()`, `EllipticCurvePublicNumbers(...).public_key()` fed from a JWK dict, `RSA.construct` |
| `loaded-certificate` | Public key taken from an X.509 certificate. | `load_pem_x509_certificate(...).public_key()` |
| `constructed-from-parsed-blob` | Reconstructed from numbers parsed from a non-JWK wire/file format. | paramiko OpenSSH blob → `RSAPrivateNumbers` |
| `parameter` | Received as a function/method parameter whose origin is outside the function. | `def sign(self, key, msg): key.sign(...)` when `key` is not resolvable |
| `attribute` | Read from an object attribute (`self.key`, `self.prepared_key`) whose assignment is elsewhere in the class. | pilot sites P01, P06, J04 |
| `env-or-KMS` | Obtained from environment variables, secret managers or KMS/HSM interfaces. | `boto3.client("kms")`, `os.environ["PRIVATE_KEY"]` |
| `unknown` | Cannot be determined. | dynamic attribute, reflection |

`attribute` and `parameter` are *proximate* provenances; the annotator additionally records the *ultimate* provenance set when it can be resolved (e.g. P01: attribute ← {generated, loaded-DER, constructed-from-parsed-blob, wire message}).

## 6. Mapping to CycloneDX 1.6 (verified 2026-11-14 against the official bom-1.6 schema, tag 1.6.1)

The 1.6 `cryptoFunctions` enum is: generate, keygen, encrypt, decrypt, digest, tag, keyderive, sign, verify, encapsulate, decapsulate, other, unknown. It has no key-agreement value, and the `padding` enum (pkcs5, pkcs7, pkcs1v15, oaep, raw, other, unknown) has no PSS. The exporter (`pqscan/export/cbom.py`) therefore uses:

| Role | Component | primitive | cryptoFunctions | Extra |
|---|---|---|---|---|
| SIGN / VERIFY | `algorithm` asset | signature | sign / verify | padding pkcs1v15, or `other` + `pqscan:padding=PSS` |
| KEY_ESTABLISHMENT | `algorithm` asset | key-agree | other | `pqscan:role=KEY_ESTABLISHMENT` |
| PK_ENCRYPT / PK_DECRYPT | `algorithm` asset | pke | encrypt / decrypt | padding oaep / pkcs1v15 |
| key-material sites (any role) | `related-crypto-material` | — | — | type private-key / public-key / key; size when known |
| UNKNOWN | as above by site kind | unknown when no role family applies | unknown | `pqscan:possibleRole` entries |

Every component carries role, tier, action, target class, rationale, policy version, provenance and evidence as `pqscan:*` properties; operation components depend on the key-material components their receiver was traced to.

Project: Post-quantum crypto scanner for Python projects. Base paper DOI 10.1145/3774748.3795653.

This document freezes how every method (external tools, simple baselines, pqscan arms) is judged at each benchmark site. It consolidates `recommendation_policy.md` v1.1 Section 5, the review-round decisions of Phase 2, and the open strict-scoring decision. | Method action | RECOMMEND, FLAG_NO_TARGET, ABSTAIN, NO_FINDING, EXECUTION_FAILURE | method output via adapters |

## 2. Primary judgment (policy v1.1 Section 5)

| Condition | Judgment | Harm |
|---|---|---|
| Method failed on the file (missing report, file the tool is measured to drop, file in the tool's own error log) | EXECUTION_FAILURE | — |
| Ineligible site, nothing reported | N/A | — |
| Ineligible site, anything reported (an abstention included) | FALSE_POSITIVE_SITE (detection level) | — |
| Eligible site, nothing reported | MISSED | — |
| ABSTAIN on an INDETERMINATE site | CORRECT | — |
| ABSTAIN on a DETERMINATE site | UNASSESSABLE (not correct, not harmful; lowers coverage) | — |
| FLAG_NO_TARGET where expected NONE | CORRECT | — |
| FLAG_NO_TARGET elsewhere | DETECTED_ONLY | — |
| RECOMMEND of the expected family | CORRECT | — |
| RECOMMEND of the other family (KEM for SIGN/VERIFY; SIG for KE/PK_*) | INCORRECT | ROLE_INCOMPATIBLE |
| RECOMMEND "already PQC" on a quantum-vulnerable non-hybrid site | INCORRECT | FALSE_ASSURANCE |
| RECOMMEND SIG/KEM where expected NONE (inventory, approved hybrid) | INCORRECT | OVER_RECOMMENDATION |
| RECOMMEND DUAL on a DETERMINATE site, or on an INDETERMINATE site | UNDECIDED | — |
| RECOMMEND a single target on an INDETERMINATE site | UNJUSTIFIED | — |

"Harmful" always means INCORRECT with a harm category. UNDECIDED, UNJUSTIFIED and UNASSESSABLE are reported separately and never folded into "harmful".

## 3. Strict sensitivity analysis (resolves open decision C2)

Pre-registered and reported in every results table next to the primary score, never instead of it:

- A primary CORRECT on a site whose expected family is KEM (key establishment or public-key encryption/decryption), where the method's text implies a direct substitution ("replace RSA with ML-KEM", "drop-in", "swap", "replaces … entirely/directly"), becomes **INCORRECT with harm UNSUPPORTED_DROP_IN**.
- Negated phrases ("no drop-in replacement", "not a drop-in") never trigger it.
- All other judgments are identical to the primary scoring.

Rationale: ML-KEM is a KEM, not a public-key encryption scheme. SP 800-227 describes key transport with a KEM only through the KEM/DEM construction, so "replace RSA encryption with ML-KEM" is unsafe advice even though the family is right. The primary scoring keeps the pre-registered v1.1 definition of harm (family incompatibility). The strict scoring tests whether conclusions change when unsafe wording also counts as harm.

## 4. Indeterminate and unassessable examples

- A site is INDETERMINATE when its role depends on a runtime value, dynamic dispatch or code outside the repository (annotation guide, Step D). The only CORRECT outcome is an abstention (or, for ineligible handling, nothing). A dual target is UNDECIDED, and a single target is UNJUSTIFIED.
- Annotators who cannot decide between DETERMINATE and INDETERMINATE after adjudication record INDETERMINATE.
- UNASSESSABLE marks a method's abstention on a determinate site. It counts against coverage, never against harm.
- Sites whose ground truth cannot be adjudicated at all (annotators and adjudicator disagree on eligibility after discussion) are excluded from scoring and listed with the reason. They are never silently dropped.

## 5. Denominators and fairness

- Every rate (correct, harmful, undecided, coverage) uses n_exec: eligible sites where the method ran. Execution failures are reported in their own column per method.
- Paired comparisons (McNemar) use only sites where both methods ran.
- Detection precision counts FALSE_POSITIVE_SITE for every method, including pqscan abstentions.
- Each external tool's file-failure behaviour is the measured profile in `benchmark/baselines_manifest.json`. A tool's silence on a file of a condition it is known to drop is EXECUTION_FAILURE, never MISSED.

## 6. Interpretation note (v1.0.1; no rule changed)

- **What a primary CORRECT means (F09).** The expected class treats KEM and KEM_DEM as one family. A primary CORRECT therefore means that the recommended **target family** is compatible with the site's role. It does not verify that the recommendation's content is a complete KEM + KDF + AEAD redesign, which recommendation policy Sec. 2 requires; the pre-registered strict sensitivity analysis adds only the drop-in-wording check. Reports state this wherever a CORRECT rate is given.
- **"Cannot be adjudicated" under the single-investigator design.** The two-annotator wording of the exclusion rule for sites whose ground truth cannot be adjudicated reads, since protocol v1.0.4 Sec. 3, as: eligibility left unresolved by the owner (`meta.unresolved` contains `eligible`). Such sites are excluded, listed and bounded (protocol Sec. 5.6).
