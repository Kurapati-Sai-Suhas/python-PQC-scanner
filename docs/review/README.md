# Human review and annotation kit

Project: Post-quantum crypto scanner for Python projects. Prepared 14 Nov 2026.

**Status: no human review or human annotation has taken place yet.** Every register in this folder is empty until a named person completes the work. AI reviews from earlier phases are recorded in the phase reports, and they do not count as human review.

## 1. Roles and who may fill them

| Role | Count | Independence requirement | Suggested qualifications |
|---|---|---|---|
| Specification reviewer | at least 1 | not a member of the build team | Python programming; security analysis; basic public-key cryptography (signatures vs. key establishment vs. encryption); ideally familiar with FIPS 203/204 at overview level |
| External annotator (annotator B) | at least 1 | not a member of the build team; has not seen pqscan or baseline output for the repositories they label | Python programming (reading classes, imports, call chains); basic cryptography as above |
| Internal annotator (annotator A) | 1 | build-team member allowed (protocol Sec. 3), but for the test split only after the pre-test freeze F1 | same |
| Adjudicator | 1 | neither annotator for the sites adjudicated; ideally the lecturer or a supervisor | security or cryptography background |

Each person registers in `review_register.md` before starting: name, or a pseudonymous ID held by the supervisor; role; relevant background in one line; any conflict of interest; date. Nobody may record approval on another person's behalf.

## 2. Specification review (taxonomy v1.0.1, policy v1.1, scoring v1.0)

Documents: `docs/specification/role_taxonomy.md`, `recommendation_policy.md` (with `pqscan/policy/policy_v1_1.yaml`) and `scoring_policy.md`.

1. Copy `forms/spec_review_form.md` to `forms/completed/spec_review_<reviewer-id>_<YYYY-MM-DD>.md`.
2. Answer every question. "No issue" is a valid answer, but a blank is not.
3. Give a verdict per document: APPROVED, APPROVED WITH CHANGES (list them) or CHANGES REQUIRED.
4. The build team responds to each requested change in the same file under "Response". A change to a frozen document creates a new version with a changelog entry. Before the pre-test freeze F1, this is allowed. After F1, it is logged and evaluated only as exploratory work.
5. The reviewer signs off the responses. The verdict and date go into `review_register.md`.

## 3. Pilot-label review (31 sites)

1. The reviewer labels `forms/pilot_label_review_blind.csv` from source only, following `docs/benchmark/annotation_guide.md`, at the pinned commits listed in the form. The existing labels (`docs/pilot/h1_pilot_sites.csv`) and all tool outputs stay hidden until the form is submitted. The form is generated by `scripts/make_review_forms.py`.
2. The submitted form is saved unchanged as `forms/completed/pilot_review_<reviewer-id>.csv` and its SHA-256 goes into the register.
3. Agreement with the existing labels is computed per field (eligible, gt_role, assessability, key_provenance): raw agreement, Cohen's κ and the confusion table.
4. Disagreements go through Section 5. The adjudicated outcome decides whether a pilot label is corrected. Corrections are new rows with a reason; the original is never overwritten.

## 4. Benchmark annotation (Dataset B; at least 300 eligible sites, at least 150 eligible test sites if achievable)

- **Candidates:** the union of the regex over-approximation, every baseline's findings and pqscan Module A detections. The list carries location and API only, with no tool attribution and no recommendation text. The candidate pool is never built from pqscan output alone.
- **Order:** development and validation repositories first. Test repositories are annotated only after the pre-test freeze F1 (evaluation protocol Sec. 6).
- **Independence:** annotators A and B label every site separately, using `forms/annotation_template.jsonl` (one JSON object per site, fields as in `docs/benchmark/benchmark_schema.json`, plus `annotator_id` and `submitted_utc`). Neither annotator sees the other's labels or any tool output before submitting.
- **Preservation:** each annotator's submitted file is kept unchanged as `labels/<split>/<repo>/raw_<annotator-id>.jsonl` and hashed immediately. For the test split, the files stay outside git until the label freeze F2.
- **Agreement:** per field, report raw agreement and Cohen's κ (target ≥ 0.70) with bootstrap CIs, the class distribution, and the initial-disagreement table before any adjudication.

## 5. Disagreement and adjudication procedure

1. A script lists every site where A and B differ on eligible, gt_role, assessability or key_provenance. This initial disagreement table is saved and hashed. It is never edited.
2. The adjudicator receives both labels and both justifications, but no tool output, and reads the source.
3. The adjudicator records one row per disputed site in `forms/adjudication_log.csv`: the final value per disputed field, the reason, whether the annotation guide was ambiguous, and the date. "Guide ambiguous" rows are collected for a guide revision. Before F1 the guide may be revised; after F1 a revision is a new version used only for new data.
4. The adjudicated label file is derived mechanically from the raw labels plus the log. Both raw files, the disagreement table, the log and the adjudicated file are kept.

## 6. What the build team must not do

- Fill any form, register row or label on behalf of a reviewer or annotator.
- Show tool outputs, or the other annotator's labels, to an annotator before submission.
- Change the system after viewing test labels or test outcomes.
